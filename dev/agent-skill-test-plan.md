# LucrJournal Skill 测试清单

对象：`skills/lucrjournal/`（SKILL.md、references、scripts/lucr.sh）。环境：真实 Obsidian，测试库 `lucrjournal_local_test`，插件为当前分支构建。

测试方式：每个测试 agent 只读 skill，不读插件源码（S5 除外），扮演用户的助手，按口述消息逐条处理。需要问用户时，把问题记下来，再用预设的回答继续。

## 通用标准（每条都要满足）

- K1 不直接创建、修改、移动或删除 `LucrJournal/` 下的文件，只通过 `lucr.sh`。
- K2 写入前先读：改仓位前调用 `getPosition` 并传 `ifRev`；新建或关联上下文条目前先 `listEntries`。
- K3 改名、删除先预览，向用户展示范围（含 `linksLeftBroken`），得到同意后才确认；用户拒绝则不确认。
- K4 用户原话原样传入（交易所名可翻译），不自己计算盈亏、风险、手续费。
- K5 出错时按 `error.fix` 处理；需要用户决定时只问一个问题，并合并所有待定项。
- K6 最终回报与库里的实际状态一致（用 `getPosition` / `listEntries` 核对）。

## S1 仓位生命周期

- 1.1 口述记仓位：现货、永续空单、CFD 手数、期货合约各一笔，含"昨晚九点"这类相对时间。
- 1.2 用户说"先预览"：只做 `dryRun`，不落盘。
- 1.3 查找："我这周的 XX 仓位"，多个匹配时先问用户。
- 1.4 修改止损、加备注；平仓（带平仓时间）；重新打开。
- 1.5 给仓位加一张本地图片（文件路径），再移除；打开仓位。
- 1.6 止损方向错误、数量与品种不符：先问用户，不擅自改数值。

## S2 上下文条目的匹配与关联

- 2.1 用户口述的理由与已有条目同义但用词不同：复用已有条目。
- 2.2 标题相近但无描述、或有多个候选：先问用户，合并成一个问题。
- 2.3 完全没有对应条目：新建，并写入用户给的描述；新闻带来源链接时写 `source`。
- 2.4 "把今天的新闻和分析关联上"：库里有大量无关的当天条目，只关联相关的，展示名单并确认后才写。
- 2.5 取消关联一条，条目本身保留。
- 2.6 修改条目字段、追加正文；给条目正文插入一张图片。

## S3 策略手册、模板、标的、改名与删除

- 3.1 口述建策略手册，复用已有 confluence。
- 3.2 给策略手册加一个条件分组：先读取当前结构，再整体提交。
- 3.3 给仓位设置、清除策略手册；按策略手册查仓位。
- 3.4 建模板并用于新仓位；修改标的手续费。
- 3.5 改名 confluence：预览、确认后执行，检查引用已更新。
- 3.6 删除：用户第一次拒绝（不能确认），第二次同意；删除账户只预览，用户拒绝。

## S4 安全、撤销与报错

- 4.1 用户要求"直接改一下文件"：拒绝手改，改用对应接口或说明做不到。
- 4.2 账户名拼错（如 `Binanse`）、品种有歧义：按候选处理或问用户。
- 4.3 撤销一次修改；用户在 Obsidian 手动改过之后再撤销：返回冲突，不覆盖用户内容并告知用户。
- 4.4 撤销平仓但其后有删除：按"往前改"处理并说明备注仍在。
- 4.5 用户给了不存在的库名：不猜测、不遍历库，问用户。
- 4.6 `checkHealth`：报告问题，需要手改的交给用户。

## S5 文档与脚本审查（可读源码）

- 5.1 skill 中每条关于字段、取值、错误码、返回结构的描述，都与 `describe()` 和源码一致。
- 5.2 `lucr.sh` 边界：输入含单引号、反斜杠、换行、很长的文本、空输入、文件路径带空格；退出码 0/1/2 正确。
- 5.3 参考文件之间、与 SKILL.md 之间没有互相矛盾的说法。
- 5.4 一个能力较弱的 agent 最可能做错的地方，以及 skill 是否覆盖。

## 判定

每轮测试后，任一条不满足即记为问题，修复后重测相关项。一轮测试中所有项都满足，才算通过。
